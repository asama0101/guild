# guild の役 SPEC（`docs/spec.md` の追補）

## 概要

- **目的**: 最初の版の役（サブエージェント）の構成、責任、道具、モデルを決め、`agents/*.md` と `skills/quest/SKILL.md` を書き始められるようにする。
- **前提**: 進め方の判断（順序・遷移・リトライ）は `guild.py` と `transitions.json` が持つ。役は『作業と報告』だけで、判断しない。
- **公式ガイドの反映**: 『1役1作業』『description は他と区別できるほど具体的に』『ツールは必要な分だけ』。非フォークのサブエージェントは会話履歴を見ないので、呼び出しのメッセージに入力のパス・合格基準・出力先を毎回書く。

## 役の構成（5役＋スキル本体）

| 名前 | 種類 | 受け持ち | 道具 | モデル（提案） |
|---|---|---|---|---|
| ギルドマスター | スキル本体（`/guild:quest`。サブエージェントではない） | 依頼の受け付け、`guild.py` の呼び出し、役の呼び出し、入力の到着の待機（質問・承認・確認・結果・判断はボードの手紙。チャットでは聞かない）、依頼の完了後に司書を呼び、候補の確認を待つ | 全部 | 利用者のモデル |
| 地図師（`cartographer`） | サブエージェント | 依頼を Todo に分解する。前提関係（`deps`）・種別（`auto`/`human`）・確認の印（`confirm`）・合格基準を決め、書庫（`archive/`）の関係する項目を引く。曖昧な点は『聞くべきこと』として返す | `Read, Glob, Grep, Write` | `opus` |
| 冒険者（`adventurer`） | サブエージェント | `auto` の Todo を実行する（調べる・書く）。報告を `reports/` に、成果物を `output/` に書く | `Read, Glob, Grep, WebSearch, WebFetch, Write, Edit` | `sonnet` |
| 斥候（`scout`） | サブエージェント | 動的ページ（JavaScript で中身が出るページ）をブラウザで読み、文字を取って成果物にする。読むだけ（クリック・入力・ログインはしない）。地図師が `needs_browser: true` を付けた `auto` の Todo のときだけ、ギルドマスターが冒険者の代わりに呼ぶ。ブラウザが1つなので同時に1人まで | `Read, Glob, Grep, Write` と、plugin 同梱のブラウザ（`.mcp.json` の Playwright MCP）の読み取り系だけ：`browser_navigate, browser_snapshot, browser_wait_for, browser_press_key, browser_take_screenshot, browser_tabs, browser_close` | `sonnet` |
| 鑑定士（`appraiser`） | サブエージェント | Todo の成果物を合格基準で判定し、`passed`/`rejected` と指摘を返す。出典の URL は WebFetch で開いて実在と内容を照合する。開けない出典が残り、出典が合格基準で求められているときは `needs_scout` を返し、ギルドマスターが斥候を確認モードで呼んでから再鑑定する（再鑑定は1回だけ）。成果物は直さない | `Read, Glob, Grep, WebFetch, Write` | `sonnet` |
| 司書（`librarian`） | サブエージェント | 依頼の完了・中止後に、報告と成果物から、書庫に残す用語・業務フロー・業務情報・個人・心得の候補を `reports/archive-draft.json` に書く。登録はしない（登録は `guild.py` と依頼主の確認） | `Read, Glob, Grep, Write` | `sonnet` |

- 受付（聞き取り）は専任の役を置かない。地図師が『聞くべきこと』（`questions`）を `plan-draft.json` に書き、ボードが「質問」の手紙にして依頼主に出す。ギルドマスターは質問せず、回答を `guild.py answers` で取り出して地図師に渡す（Q7。のちに、質問はすべてボードで行うと決めた）。
- 記録（旧ノウハウ）は、書庫（`archive/`）に置き換え、専任の司書を置いた（`docs/archive-spec.md`）。全役が作業の前に `archive/index.md` を見て、使った項目を報告の「使った書庫の項目」に書く。心得（`lessons/`）は役が読まない。
- 旧版の『受付嬢』は引き継がない。受付の役を作るときは、性別を含まない『受付係』にする。

## モデルの方針と割り当て（Q12-D）

- 方針：探索・検索のような単純な作業は `haiku`、ほとんどの作業は `sonnet`、複雑な設計判断だけ `opus`。
- 割り当て（提案）：
  - 地図師：分解は依頼ごとに1回で、後工程すべてに響く設計判断なので `opus`。
  - 冒険者：調査も文書作成も含む『ほとんどの作業』なので `sonnet`。
  - 鑑定士：Todo ごとに繰り返す判定で、『薄くならない』の要。公式に判定役の推奨はないが、判断の質を優先して `sonnet`。
- エイリアス（`opus` `sonnet` `haiku`）は提供元の推奨版に更新される。特定の版に固定したくなったらモデルIDを書く。
- 見直しのきっかけ：費用が過大、または特定の役の質が落ちたとき。

## 冒険者を分ける条件（Q5-C）

最初は1役。次のいずれかを満たしたら、『調べる冒険者（Web を読む、`haiku` または `sonnet`）』と『書く錬金術師（Web なし）』に分ける。

1. 書く Todo の大半が、外部サイトを読まずに済むと分かった（Web を読む権限を調べる役に閉じ込められる）。
2. 合格基準で『出典がない』と『文章が浅い』が、別々に繰り返し不合格になった。

分けるときは、追加の理由を決定ログに書く。

## 受け渡し（Q8-A）

- 各役は `guild/<依頼>/reports/<Todo ID>-<役>.md` に、固定の見出しで報告を書く。返り値は『書いた場所』と一言の結果だけ。
- 報告の見出し：`## 結果`、`## 根拠・出典`、`## 未確認`、`## 次に必要なこと`（斥候は「未確認」の代わりに `## 読めなかったこと`。鑑定士は `## 判定`、`## 合格基準ごとの確認`、`## 指摘`、`## 斥候に確認してほしいこと`、`## 出典の確認`、`## 成果物を変更していない`）。
- 呼び出しのメッセージには、入力のパス、合格基準、出力先を毎回書く（サブエージェントは会話履歴を見ない）。
- `plan.json` を書けるのは `guild.py` だけ。地図師は分解結果を `reports/plan-draft.json` に書き、ギルドマスターが `guild.py` の取り込みコマンドで `plan.json` にする。

## agents/*.md の書式

- `name` と `description` を必ず書く（片方が欠けるとスキップされることがある）。`description` は、いつ使うかを具体的に書き、他の役と区別できるようにする。
- frontmatter は `name` `description` `tools` `model` に絞る。プラグインでは `permissionMode` `hooks` `mcpServers` は無視される。
- 本文は役の指示。守らせたい規則は、呼び出しのメッセージでも繰り返す。
- `claude plugin validate` で書式を検査する。

## 受入条件

1. `agents/` に `cartographer.md` `adventurer.md` `scout.md` `appraiser.md` の4ファイルがあり、各ファイルに `name` `description` `tools` `model` がある。
2. 各役の `tools` が上の表のとおりで、鑑定士・地図師に `Edit` がなく、地図師に Web 系のツールがない（鑑定士は WebFetch のみ）。
3. 役は進め方の判断（順序・遷移・リトライ）をしない。判断は `guild.py` の出力に従う。
4. 各役の報告が `reports/<Todo ID>-<役>.md` に固定の見出しで残る。
5. 地図師の出力が、`guild.py validate` を通る `plan-draft.json` になっている。
6. 鑑定士が成果物を書き換えない（指示で禁止し、報告に『成果物を変更していない』と書く）。
7. `skills/quest/SKILL.md` は 500 行未満で、役の詳細は `agents/*.md` に置く。

## 非目標（最初の版では作らない）

- 受付係（聞き取りの専任）、錬金術師、鍛冶師、魔法使い。
- 役ごとのモデルの自動最適化。
- 役の自動追加。

## リスク

| リスク | 対策・方針 |
|---|---|
| 冒険者が『何でも屋』になり、description が曖昧になる | 分ける条件を決めておく（上記）。`description` は『auto の Todo を実行し、報告と成果物を書く』に絞る。 |
| 鑑定士・地図師に `Write` を与えるため、成果物や `plan.json` を書き換えるおそれ | 指示で禁止し、報告に変更の有無を書く。`plan.json` は `guild.py` だけが書く。実際に起きたら、`Write` を外して返り値で受け取る形にする。 |
| 受け渡しの見出しが崩れる | 報告の見出しを固定し、`guild.py` に報告の見出しの検査を足すことを検討する。 |
| モデルの割り当てで質や費用が想定とずれる | 見直しのきっかけを決めておく。`/tasks` で実際のモデルを確認する。 |
| 利用者の環境（組織の許可リスト、提供元）で、指定したモデルが使えず置き換わる | 置き換わっても動く前提で書く。警告が出たら見直す。 |

## 役の呼び方についての検証記録（v0.1.30）

「呼び出し中の印（`dispatched`）」を入れて検証したが、効果が確認できなかったため外した。

- 実機（`claude -p "/guild:quest"`、旧版 v0.1.29 と印つきの試作を各3回。3依頼・14 Todo。長い作業・斥候・人の作業・遅れた承認を含む）で、完了までの時間は旧 185〜218 秒・試作 184〜200 秒、役の呼び出しは両方21回で、差はなかった。
- 旧版に、約6秒ごとに25通の手紙を流して周回を何十回も回しても、二重呼び出しは0だった（2回）。
- 実機の Agent ツールは、呼ぶと即座に制御が返り、役は終わった順に通知で戻る。15秒の役は、同時に呼んだ75秒の役を待たずに戻った。
- 未検証：会話が長くなって文脈が圧縮されたあと、中断後の再開で、ギルドマスターが動いている Todo を呼び直すか。再現したら、印の導入を再検討する。
- 斥候が依頼をまたいで同時に1人までなのは、ブラウザが1つのため（変わらず）。同時に動かす数の上限は `guild.py` にはない。
