# SPEC：guild 0.1（新規設計）

状態：**承認済み（依頼主が「実装開始」を指示。要承認の項目も含む）。実装済み：0.1.0〜0.3.0（実ブラウザ・実 Claude Code での通し確認は未実施）**。

この SPEC は、guild を**ゼロから作り直す**ための設計書である。1.7 以前のコード・データ・テストは引き継がない（参考にするだけ）。互換も移行も考えない。バージョンは 0.1.0 から数える。この文書だけを読めば、実装を始められるようにする。

## 1. 目的と範囲

**guild とは**：Claude Code のプラグイン。依頼主（非エンジニアの日本語話者）の依頼を、ギルドの仲間（役ごとのサブエージェント）が分担して片付け、成果物（納品物）を納める。

**目的**
1. 依頼は「クエスト」1 本に統一する。
2. クエストは「達成条件に分解 → 道のりを決める → 依頼主が承認 → 冒険 → 達成条件をクリア」の順に進む。達成条件がそのまま納品物になる。
3. 依頼主に見せるものは、**簡易な日本語と図解**を主にする。
4. 状態は 1 か所（`board.json`）に持ち、遷移は 1 つのデータ（`transitions.json`）で決め、機械が検査する。
5. **人がやることは、依頼の入力、承認①②（不可逆な操作があれば③）、必要な質問への返事だけにする**。ほかの質問と確定は進行を止めず、期限が来たら推奨案で進む（5.7）。
6. **低コスト**：1 クエストあたりの Claude の呼び出し回数とトークンを、品質を落とさない範囲で最小にする（2.1）。
7. **使うほど良くなる**：失敗・好み・用語・実績を蓄積し、次回以降に読む（15 節）。

**前提**
- 動かす場所：Obsidian の vault の中の `guild/`（vault は任意のフォルダでよい）。
- 依頼主の画面：`guild/board.html`。Edge または Chrome で開く（フォルダの読み書きに `showDirectoryPicker` を使う）。サーバは持たない。
- Python：標準ライブラリだけ。Windows・Mac・Linux で動く。
- 呼び方：`/guild:init`、`/guild:quest`、`/guild:quest auto`、`/guild:workshop`、`/guild:help`。

## 2. 設計の原則
1. **状態の唯一の源は `board.json`**。書けるのは `board.py` だけ（排他ロックつき）。ギルドマスター（メインセッション）も直接は書かない。
2. **遷移の唯一の正は `transitions.json`**。`board.py` が、無い辺・許されない役・許されない書込先・満たされない条件を拒否する。SKILL.md の表と図は、ここから生成する。
3. **役ごとに書ける場所を固定する**（7.6 の権限）。
4. **サブエージェントは返答が 1 回で、対話できない**。対話はメインセッションが担当し、サブには確定した仕様だけを渡す。
5. **トークンを節約する**（2.1）。SKILL.md は 500 行以下。分岐は `references/` に分ける。
6. **依頼主向けの文は簡易日本語**。文章より図で伝える（12 節）。
7. **事実と推論を分ける**。冒険者は事実を集め、錬金術師が推論し、鑑定士は「事実が出典と合うか」と「推論が前提を明示しているか」だけを確かめる（推論の当否は依頼主が承認②で決める）。事実・推論・依頼主の意見・未確認は、すべての蓄積（納品物・魔導書・人物伝）で区別して書く（4.1）。
8. **ファイルは読み手で分ける**（7.1）。依頼主が見るものと、ギルド員（LLM）が読むものと、機械専用のものを、混ぜない。
9. **入力されたデータは取り扱ってよいものとして扱う**。何を入れるかの責任は依頼主が持つ（トークン・鍵・パスワードなどを入れるかどうかも依頼主が判断する）。guild は、入力の中身を検査して拒否したり、質問で止めたりしない。この前提を README と `/guild:help` に書き、依頼主に伝える。

## 2.1 低コストの方針
金額はモデルの料金で変わるため、SPEC には書かない。実績は `usage.jsonl`（呼び出しごとの役・モデル・トークン）で見る。典型的な 1 クエスト（達成条件 3 件、手直しなし）の呼び出しは約 12〜17 回と見積もる（実測で見直す）。
1. **既定のモデルは sonnet**。haiku は機械的な抽出（魔法使い）。opus は既定では使わず、**錬金術師だけ**を次のどれかで上げる：(a) 達成条件の `effort` が「高」（占い師が分解のときに付ける。依頼主が「念入りに作る」で上書きできる。達成条件ごと）、(b) 要手直しの 2 回目で、鑑定の指摘が「矛盾」「誤り」（推論の質）のとき。
2. **LLM を使わない部分は `board.py` に寄せる**：クエスト票と、依頼主向けの定型文（質問の骨組み、知らせ）の生成、鑑定前の機械検査（`pre-check`）、納品物どうしの機械照合（`cross-check`）、道のり検査、魔導書の検索、文の検査、期限の処理（`tick`）、整理候補の抽出（`housekeeping`）。
3. **呼び出しを減らす**：
   - `pre-check` が NG なら、鑑定士を呼ばずに要手直しにする。
   - クエスト全体の最終鑑定は、`cross-check` が矛盾の疑いを見つけたときと、依頼主が頼んだときだけ行う（既定は省略）。
   - 魔法使いと吟遊詩人は、クエストの達成時に、やることがあるときだけ 1 回ずつ呼ぶ。
   - 冒険者と錬金術師は、事実の収集と推論を分けるため、統合しない。代わりに冒険者の報告を「事実表」に固定して小さくする（3 の「渡す文脈」）。
4. **渡す文脈を絞る**：
   - 依頼書には素材の中身でなく場所（パス）を書く。
   - 魔導書は、`board.py` が達成条件の語で `spellbook-find` を実行し、**一致した項目（1 回 5 件まで）だけ**を依頼書に付ける。ギルド員は索引を読まない。
   - 冒険者の報告は「事実表」（1 行 1 事実、出典つき）に固定し、1,500 字までにする。
   - 鑑定士には、納品物と出典の一覧だけを渡す（冒険者の報告は渡さない）。
   - 魔法使いには、報告書の `## 用語` 節と知見メモの該当節だけを `board.py` が抜き出して渡す。
   - 毎回読むものに行数の上限を置く：掟は役ごとのファイルだけ、1 ファイル 20 行まで。人物伝は `board.py profile-brief` が作る 10 行の要約。教訓帳は `board.py lessons-brief` が該当する分類だけを抜き出す。ギルドマスターの `get --summary` は、進行中のものだけを各 2 行、最大 30 行。
5. **上限を置く**：
   - 要手直しは、達成条件ごとに 3 回、クエスト全体で 6 回まで。依頼主の「直す」も数える。超えたら、依頼主に聞く（続ける／工房で直す／諦める）。
   - 道のりの差し戻し（`fix_kind: goal`）は、クエストごとに 2 回まで。
   - 1 回の実行で呼ぶサブエージェントは 20 まで（手直しの呼び出しも数える）。超えたら、その回を止める。次の回は続きから始め、質問は出さない。同じクエストで 3 回続けて予算で止まったら、依頼主に聞く。
   - 自動実行は、Claude が必要な作業がなければ Claude を呼ばない（14 節）。
6. **見える化**：`board.py usage` が `usage.jsonl` を集計し、クエストの詳細に呼び出し回数と概算トークンを出す。`board.py calib` が、effort 別の鑑定 NG 率・手直し回数・見積と実績の比を集計し、占い師の依頼書に「見積の補正係数」を 1 行で渡す。opus に上げる条件の見直し案も出す（0.2.0）。
7. SKILL.md の本体は 300 行以下を目標にする（上限は 500 行）。分岐は `references/` に分け、必要なときだけ読む。

## 4. 役職
モデルとツールは**仮決め**（実装時に見直す）。最小のツールだけを渡す。役の ID（`transitions.json` の `actor`）は、`guildmaster`・`client`（依頼主）・`workshop`（工房中のメイン）・`receptionist`・`fortune_teller`（占い師）・`adventurer`・`alchemist`・`smith`・`appraiser`・`wizard`（魔法使い）・`bard`（吟遊詩人）。

| 役 | モデル | ツール | 責務 | 書ける場所 |
|---|---|---|---|---|
| 受付嬢 | sonnet | Read, Glob, Grep, Write | 依頼主の窓口。依頼の聞き取り（grilling）、分からない語の拾い出し、ギルド員の自由な質問の整形（定型で足りないときだけ）。定型の質問と知らせは `board.py` のひな形が作る。依頼主向けの文は、簡易日本語にそろえる | 自分の報告書 |
| 占い師 | sonnet | Read, Glob, Grep, Write | 返事がそろったあとの分解。達成条件・`done_when`・前提・所要見積（補正係数を使う）・`effort`・納品物の形・設計図を決める（締切の逆算と道のりの検査は `board.py`） | 自分の報告書 |
| 冒険者 | sonnet | Read, Glob, Grep, Write, WebSearch, WebFetch | 素材と、依頼書に付いた魔導書の項目を読み、**事実だけ**を調べて持ち帰る。報告は「事実表」で返し、末尾に log 節（やったこと［簡易日本語 1〜3 行］／判断／未解決）を付ける | 自分の報告書 |
| 錬金術師 | sonnet（条件つきで opus） | Read, Glob, Grep, Write, Edit | 納品物の**中身**（文章・分析・推論）を Markdown で作る。書式は 4.1 | `output/` |
| 鍛冶師 | sonnet | Read, Glob, Grep, Write, Edit, Bash, Skill | 納品物の**器**。錬金術師の Markdown を Word・Excel・PowerPoint・PDF にし、`templates/` に合わせる。事実・推論の区別は「根拠一覧」の付録に残す | `output/` |
| 鑑定士 | sonnet | Read, Glob, Grep, Write, Bash（読み出し専用） | 達成条件で合否を決める。事実が出典と合うか、推論が前提を明示しているか、納品物どうしに矛盾がないかを見る。指摘は `fix_kind`・`point_code`・`point` で書く。クエストの最終鑑定も行う | 自分の報告書 |
| 魔法使い | haiku | Read, Glob, Grep, Write, Edit | 魔導書の番人。業務用語・設備・取り決めを**候補**として書く。必ず出典を付ける | `spellbook/` |
| 吟遊詩人 | sonnet | Read, Glob, Grep, Write | クエスト達成時に、やることがあるときだけ 1 回：bad の理由を教訓にする、好みを人物伝の案にする、依頼主が頼んだインタビューの質問づくりと整理 | 自分の報告書 |

**4.0 報告書の決まり**
- 報告書は**ギルド員が読み書きする内部ファイル**。依頼主には見せない。
- 節名は固定する：`## 聞き取りの問い`、`## 達成条件案`、`## 依頼主への質問`、`## ギルド員への答え`、`## result`（冒険者は事実表）、`## 依頼主への報告`、`## 止まっていること`、`## log`、`## 用語`、`## fix_kind`。
- 依頼主向けの文は、`board.py` が決まった節（`## 依頼主への質問`、`## 依頼主への報告`、log 節の「やったこと」、`## fix_kind` の `point`）だけを抜き出して `board.json` に写す。画面とクエスト票は、`board.json` のその値だけを使う。

**4.1 事実と推論の書式**
- **冒険者の事実表**（`## result`）：1 行に 1 つの事実。`- 事実｜出典（素材のパス#箇所、または URL）｜取得日`。依頼主の指示や意見は書かない（納品物の「依頼主の指定」に回す）。確かめられなかったことは `- 未確認｜理由`。
- **納品物（Markdown）の節**を固定する：
  - `## 事実`：各行の末尾に `[出典: …]`。
  - `## 推論`：各行の末尾に `[前提: 事実の番号]` と `[確度: 高|中|低]`。
  - `## 依頼主の指定`：依頼主の指示・意見・条件。
  - `## 未確認`：確かめられなかったこと。事実として書かない。
- `pre-check` が、出典のない事実の行と、前提のない推論の行を検出する。
- **鑑定士の線引き**：確かめられる範囲は、素材・魔導書・URL（再取得できるもの）。確かめられない範囲（依頼主の内部事情、将来の見込み、非公開資料）は、「未確認」に書かれているかだけを見る。
- **魔導書の項目**：`sources`（1 件以上。なければ書けない）、`basis`（原文／推論）、`confidence`（高／中／低）、`verified_on`。
- **人物伝の項目**：`evidence`（依頼主の発言の引用、または納品物の id と観察した回数）、`kind`（明言／観察／推測）。推測は、2 回以上観察されるまで案のままにする。

## 5. フロー

### 5.1 クエストの状態
| 状態 | 画面での言い方 | 意味 |
|---|---|---|
| 受付 | 聞き取り中 | 受付嬢が聞き取り中 |
| 分解中 | 計画を作っている | 占い師が達成条件・道のりを作る |
| 承認待ち | あなたの承認を待っている | 道のりの承認（承認①）待ち |
| 進行中 | 進めている | 達成条件をギルド員が片付けている |
| 最終鑑定 | 全体を確かめている | 達成条件どうしの矛盾を鑑定士が見る |
| 達成 | 達成 | 終了 |
| 失敗 | 達成できなかった | 依頼主が「諦める」を選んだ。終了 |
| 中止 | 中止 | 依頼主が取り下げた。終了 |
| 保留 | 止めている | 依頼主が止めた。再開できる |

| 辺 | 役 | 条件（述語） |
|---|---|---|
| 受付→分解中 | guildmaster | `no_open_questions` |
| 分解中→承認待ち | guildmaster | `has_goals`, `acyclic`, `all_have_done_when` |
| 承認待ち→進行中 | client | `approval_recorded(route)` |
| 承認待ち→分解中 | client | 「やり直す」 |
| 進行中→分解中 | guildmaster | `fix_kind_goal`, `replans_lt_limit`。達成済みの達成条件は達成のまま、ほかは案に戻す。承認①をやり直す |
| 進行中→達成 | guildmaster | `all_goals_done`, `cross_check_clean`（最終鑑定を省く） |
| 進行中→最終鑑定 | guildmaster | `all_goals_done`, `cross_check_suspect` または依頼主の希望 |
| 最終鑑定→達成 | appraiser | 達成条件どうしに矛盾がない |
| 最終鑑定→進行中 | appraiser | 矛盾があり、直す達成条件を指定する（その達成条件は 達成→要手直し） |
| （受付・分解中・承認待ち・進行中・最終鑑定）→保留 | client | 保留前の状態を `status_before_hold` に残す |
| 保留→（保留前の状態） | client | 再開する |
| （受付・分解中・承認待ち・進行中・最終鑑定・保留）→中止 | client | `dependents_confirmed` |
| 進行中→失敗 | client | 失敗した達成条件で「諦める」を選んだ |

- **保留中**は、新しい達成条件を出発させない。すでに動いている呼び出しは終わらせ、結果だけ記録する。
- 失敗した達成条件があると、クエストは `blocked_on: client` になり、質問が出る（状態は進行中のまま）。

### 5.2 達成条件の状態
| 状態 | 画面での言い方 | 意味 |
|---|---|---|
| 案 | 計画の案 | 占い師が作った案。承認前 |
| 待機 | 順番を待っている | 承認済み。前提・同時数・触るノートの重なりを待つ |
| 冒険中 | 冒険者が作業している | 冒険者が事実を集め、錬金術師・鍛冶師が納品物を作る |
| 鑑定中 | 鑑定士が確かめている | |
| 要手直し | 直している | 鑑定が NG、またはエラー。補正して冒険中に戻る |
| 確認待ち | あなたの確認を待っている | 納品物の承認（承認②）待ち |
| 実行承認待ち | あなたの実行の承認を待っている | 元に戻せない操作の承認（承認③）待ち |
| 達成 | 達成 | 終了（最終鑑定で戻されることがある） |
| 失敗 | 達成できなかった | 承認③の拒否、または諦め。やり直せる |
| 中止 | 中止 | 取り下げ。終了 |

| 辺 | 役 | 条件（述語） |
|---|---|---|
| 案→待機 | guildmaster | 承認①が通った |
| 待機→冒険中 | guildmaster | `deps_done`, `slot_free`, `no_overlap`。出発順は余裕が小さい順→優先度→番号 |
| 待機→冒険中（工房） | workshop | `deps_done`。依頼主が工房で作ると選んだ |
| 冒険中→鑑定中 | guildmaster | `output_present`, `report_present`, `precheck_ok` |
| 冒険中→要手直し | guildmaster | 理由：`report_error`／`precheck_ng`／`no_report`／`timeout`（障害を含む） |
| 冒険中→確認待ち（工房） | workshop | `precheck_ok`。依頼主が鑑定を省くと選んだ |
| （待機・冒険中・要手直し）→案 | guildmaster | クエストが分解中に差し戻された |
| 鑑定中→確認待ち | appraiser | `done_when_met` |
| 鑑定中→要手直し | appraiser | `fix_kind` と `point_code` を書く |
| 要手直し→冒険中 | guildmaster／workshop | `retries_lt_limit`。上限なら、`blocked_on: client` にして質問（続ける／工房で直す／諦める） |
| 要手直し→失敗 | client | 「諦める」 |
| 失敗→要手直し | client | 「やり直す」 |
| 確認待ち→達成 | client | `approval_recorded(output)`, 元に戻せない操作がない |
| 確認待ち→要手直し | client | 「やり直す」。直す点を `fix_kind: brief` で書く。手直しの回数に数える |
| 確認待ち→実行承認待ち | client | `approval_recorded(output)`, `needs_execute` |
| 実行承認待ち→達成 | client | `approval_recorded(execute)`。メインセッションが実行し、結果を冒険日誌に残す |
| 実行承認待ち→失敗 | client | 拒否 |
| 実行承認待ち→要手直し | guildmaster | 実行がエラーになった |
| 達成→要手直し | appraiser | 最終鑑定で矛盾が見つかり、直す達成条件として指定された |
| （案・待機・冒険中・鑑定中・要手直し・確認待ち・実行承認待ち・失敗）→中止 | client | `dependents_confirmed` |

- **補正（`fix_kind`）**：`input`（素材・資料室の選び直し）／`brief`（依頼書の書き換え）／`goal`（達成条件の見直し。クエストを分解中へ差し戻す）。
- **分類コード（`point_code`）**：`欠落`／`矛盾`／`誤り`／`形式`／`出典なし`／`範囲外`。`point_code` と対象（ファイル・節）が同じなら、同じ指摘とみなす（5.3）。
- **待ち**は状態にせず、属性 `blocked_on`（`client`／`guild`／空）で持つ。クエストは、中の達成条件の `blocked_on` を集めて表示する。
- **失敗・中止した達成条件に依存する後続**は、自動で `blocked_on: client` になり、質問が出る：「この達成条件をやり直す」「この達成条件なしで進める（前提から外す）」「後続も中止する」。推奨案は付けない。
- **依頼主の「直す」**も、手直しの回数に数える（2.1-5）。

### 5.3 掟の追加と見直し
- 同じ指摘（`fix_kind`＋`point_code`＋対象が同じ）が **2 回目**になったら、鑑定士が掟の案を 1 行書き、ギルドマスターが質問（`kind: rule`）を出す。承認されたら `.system/rules/<役 ID>.md`（全員向けは `_all.md`）に足す。
- 掟には、`id`・追加日・根拠（`fix_kind`＋`point_code`）・適用後の再発数を持たせる。1 ファイル 20 行まで。
- 半年再発しない掟、または適用後も再発が減らない掟は、見直し候補として質問に出す（`housekeeping`）。掟どうしが矛盾したときは、依頼主が決める。

### 5.4 グラフ（依頼主の参考グラフとの対応）
番号は、依頼主の参考グラフ（1 データ取得、2 処理・生成、3 検証・レビュー、3.5 パラメータ補正、4 実行／投入）のもの。**正は `gen-transitions` が `transitions.json` から作る図**で、ここは概略である。
```
[START] → 1.データ取得 → 2.処理・生成 ─エラー／pre-check NG→ 3.5 補正 ─┐
                              │                                          │
                              ▼                                          │
                    3.検証・レビュー（鑑定）─NG→ 3.5 補正 ───────────────┤ （冒険中へ戻る）
                              │OK                                        │
                              ▼                                          │
                    承認②（確認待ち）─やり直す→ 3.5 補正 ────────────────┘
                              │承認
                              ▼
                    needs_execute？ ─いいえ→ [END]
                              │はい（board.py が自動で分岐）
                              ▼
                    4.実行（承認③）─拒否→ 失敗処理（失敗→やり直し／諦め）
                              │承認
                              ▼
                       実行 → [END]
```

### 5.5 `transitions.json`
```json
{ "version": 1,
  "quest": [ {"from":"受付","to":"分解中","actor":["guildmaster"],"guards":["no_open_questions"],"note":"聞き取りが終わり、未回答の問いがない","writes":["board"]} ],
  "goal":  [ {"from":"鑑定中","to":"確認待ち","actor":["appraiser"],"guards":["done_when_met"],"note":"done_when を満たす","writes":["board","reports"]} ] }
```
- `guards` は述語の ID の一覧で、`board.py` が評価する：`no_open_questions`、`has_goals`、`acyclic`、`all_have_done_when`、`approval_recorded(scope)`、`replans_lt_limit`、`all_goals_done`、`cross_check_clean`、`cross_check_suspect`、`dependents_confirmed`、`deps_done`、`slot_free`、`no_overlap`、`output_present`、`report_present`、`precheck_ok`、`retries_lt_limit`、`done_when_met`、`needs_execute`、`fix_kind_goal`。`note` は人が読む説明で、検査しない。
- **`client` の辺**は、`answers/` に、対応する質問の id と scope が一致する回答の記録があるときだけ通す（`approval_recorded`）。誰かが `board.py` を直接呼んでも、記録がなければ拒否する。
- `writes` の値：`board`／`reports`／`output`／`quest_md`／`adventure_log`／`spellbook`／`shared`／`profile`／`rules`／`templates`／`inputs`／`lessons`。7.6 の場所と 1 対 1 で対応する。
- 生成物：SKILL.md の遷移表、状態図（SVG）、5.4 の図。

### 5.6 障害・排他・復旧
- **サブエージェントの失敗・無返答・タイムアウト**：報告書がない回として扱い、`冒険中→要手直し`（理由 `no_report`／`timeout`）にして、手直しの回数に数える。
- **予算の超過**：その回を止める。次の回は続きから始める（2.1-5）。
- **排他**：`board.json` を書く前に `.system/board.lock` を取る。画面は `board.json` を書かず、`requests/` と `answers/` にだけ書く。
- **破損への備え**：書く前に `.system/backup/board.json.1〜3`（3 世代）を残す。壊れた JSON は終了コード 1 で止め、`board.py recover` が直近の世代から戻す。
- 予算で止まったときの知らせの文例：「作業が多いため、いったん止めました。次の回で続きから進めます。」

### 5.7 放置の扱い（人を待って止まらないために）
- 質問には、`due`（期限。既定は 3 日後）と、あれば `default`（推奨案）を持たせる。
- `board.py tick` が、期限が来た質問を処理する（`apply-simple` の中で毎回実行）：
  - 推奨案がある質問（聞き取りの選択、確認、魔導書・人物伝の確定、掟の案、資料室の移動、設計図化、整理候補）は、推奨案で進める。確定・提案の類は、候補のまま使うか、見送りにする。
  - **承認①②③は自動で進めない**。期限が来たら「承認待ちです」と知らせる（再通知は 3 日ごと）。承認③は、14 日たったら保留にする。
  - 推奨案がない質問は待つ。14 日たったら、クエストを保留にして知らせる。
- 依頼主が何もしなくても、止まっていることは知らせ（画面の先頭と、クエスト票の「あなたがすること」）に出る。

### 5.8 人が介在する点（一覧）
| 種類 | 点 | 止まるか |
|---|---|---|
| 入力 | 依頼を出す、素材を足す | — |
| 必須の承認 | ①道のり、②納品物 | 止まる |
| 条件つきの承認 | ③実行（元に戻せない操作があるとき） | 止まる |
| 質問（止まる） | 聞き取りの要点、手直しの上限・失敗時の判断、予算で 3 回続けて止まったとき | 推奨案がなければ止まる |
| 質問（止まらない） | 魔導書・人物伝の確定、掟の案、資料室の移動、設計図化、整理候補、good／bad | 止まらない。期限後は推奨案か見送り |
| 任意 | 工房、保留、中止、最終鑑定の希望、「念入りに作る」 | — |

## 6. 1 回の流れ（`/guild:quest`）
1. **冒頭**：`board.py` が無い・古ければ写す。`board.py apply-simple`（`tick` を含む）を実行し、`board.py need-claude` で Claude が必要か確かめる。必要なら `get --summary` で要約を読む。前の回が途中なら続きから。
2. **取り込み**：`requests/` と `answers/` の記録を読む。同時数・優先度・効き目の設定（M・P・G）、評価（E）、魔導書の確定（D）、取り下げ（C）で `board.py` だけで済むものは、Claude なしで取り込む。
3. **受付**：新しいクエストは `board.py add-quest` で作り、フォルダ（`input/`・`output/`・`adventure log/`・`quest.md`）を作る。受付嬢が聞き取り、問いは質問に出す。クエスト以外の登録経路はない。単純な依頼も、達成条件が 1 つのクエストになる。
4. **分解**：占い師が（返事がそろったあとに）達成条件・`done_when`・締切・前提・触るノート・納品物の形・`effort`・設計図を決める。`board.py route-check` が、閉路・前提の欠け・締切の逆算を検査する。
5. **承認①**：依頼主が道のり図を見て承認する。
6. **冒険**：条件を満たす達成条件から出発する（同時数の範囲）。`board.py` が魔導書の項目を選んで依頼書に付ける。冒険者が事実表を作り、錬金術師が納品物を作り、必要なら鍛冶師が器にする。
7. **質問の取り次ぎ**：ギルド員の質問は、定型は `board.py` が、自由な質問は受付嬢が、簡易日本語にして質問に出す。
8. **鑑定**：`pre-check` が機械で検査する。OK なら鑑定士が `done_when` で合否を決める。NG なら要手直し（5.2）。
9. **承認②**：OK なら依頼主が納品物を確認し、good／bad と一言を付ける。
10. **記録**：ギルドマスターが冒険者の log 節を `board.py log-append` で冒険日誌に追記する。`board.py render-quest` がクエスト票を作り直す（LLM を使わない）。
11. **締め**：すべて達成したら、`cross-check` で矛盾を調べる（疑いがあれば最終鑑定）。クエストが達成する。`board.py` が、結果と止まっていることの知らせを定型で作る。
12. **蓄積**：クエストが達成したら、やることがあるときだけ、魔法使いが魔導書の候補を書き、吟遊詩人が教訓と人物伝の案を書く。資料室へ移す候補は `board.py shared-candidates` が出す。
13. **片付け**：取り込み済みの依頼と、処理済みの知見メモを `済/` に移す。達成・中止から 30 日たったものを退避する。

`/guild:quest auto` は、同じ流れを人の確認なしで進める（確認が要る点は質問にして止まる）。

### 7.2 `board.json`
```
{ "schema_version": 1, "python": "...", "vault_path": "...",
  "limits": { "max_active": 4, "retries": 3, "rework_total": 6, "replans": 2, "budget": {"max_calls": 20} },
  "last_ids": {"Q":0,"G":0,"A":0,"F":0,"I":0},
  "quests": { "Q1": {...} }, "goals": { "G1": {...} },
  "questions": [ ... ], "feedbacks": { "F1": {...} }, "interviews": { "I1": {...} },
  "profile_pending": 0, "notices": [ ... ] }
```
- **quest**：`id, title, detail, status, status_before_hold, blocked_on, priority(優先|通常), due, goals[], route[](達成条件 id の順), dir, requested_at, approved_at, rework_total, replans, budget_stops, log[]`。
- **goal**：`id, quest, title, effort(低|中|高), done_when[1〜3], deadline, estimate_min, actual_min, depends_on[], status, blocked_on, form(おまかせ|回答だけ|ノート|テキスト|Word|Excel|PowerPoint|PDF|その他), template, output_path, needs_execute(bool), notes_touched[], retries, findings[{fix_kind,point_code,target,point}], refs[], log[{time,who,edge,text}]`。
- **question**：`id, kind(choice|approval|todo|confirm|rule|term), scope(route|output|execute|none), quest, goal, text, diagram, options[{label,reason,recommended}], default, due, status(未回答|回答済|保留), answer, comment`。
- **feedback**：`{quest, goal, score: good|bad, reason, comment}`。**interview**：`{topic, questions, answers, status}`。
- **notice**：`{time, text, stops[]}`（最大 20 件）。
- 書込は排他ロックを取り、一時ファイルに書いて `os.replace`。UTF-8、`ensure_ascii=False`。書くたびに `updated` を更新。壊れた JSON・不明な id・不明な状態は終了コード 1 で止める。

### 7.3 `requests/`（依頼主→ギルド）
ファイル名は `<接頭辞><日時>.json`。`kind` で分ける。質問への回答は `answers/` に書く（`requests/` には入れない）。
| 接頭辞 | kind | 中身 |
|---|---|---|
| R | quest | 依頼の本文、期限、納品物の形、添付（`files/R<日時>/`） |
| M | setting | 同時数（1〜8）。新しいものが勝つ |
| P | priority | クエストの優先度 |
| G | goal_setting | 達成条件の「念入りに作る」（`effort: 高`） |
| C | cancel | 取り下げ（後続があれば、確認の質問を作る） |
| E | evaluation | good／bad と一言、理由 |
| D | spellbook | 魔導書の項目の確定／修正／保留 |
| U | upload | 素材・資料室への追加ファイルの通知 |
- `M`・`P`・`G`・`C`・`E`・`D` は、Claude を呼ばずに `board.py apply-simple` で取り込む。`R` と `U` と、答えのあった質問が、Claude を呼ぶ理由になる。

### 7.4 クエスト票（`quest.md`）
**役目**：依頼主が、クエストがどう進んでいるかを見るための記録。中身は「目的」「達成条件」「達成条件が完了するまでの記録」と、依頼主がやること。`board.py render-quest` が `board.json` と冒険日誌から作る（LLM を使わない）。状態が変わるたびに作り直す。

**節**
1. **目的**：1 文。
2. **達成条件**：道のりの順に並べた表（順・達成条件・締切・いまの様子）。納品物があれば、ファイル名でリンクを付ける。
3. **記録**：達成条件ごとに、日時つきで 1 行ずつ、完了までの経過を書く。
4. **あなたがすること**：依頼主の返事や確認が要るものだけ（質問、承認、納品物の確認）。何もなければ「いまはありません」。

**例**（文は 12 節の規則に合わせてある）
```markdown
# 取引先向け見積書

## 目的
取引先 A 社に出す見積書を、3 月 15 日までに作る。

## 達成条件
| 順 | 達成条件 | 締切 | いまの様子 |
|---|---|---|---|
| 1 | 単価表を整理する | 3月8日 | 達成（[単価表.xlsx](output/単価表.xlsx)） |
| 2 | 見積書の本体を作る | 3月12日 | あなたの確認を待っている |
| 3 | 確認用の PDF を作る | 3月14日 | 順番を待っている |
```

## 8. 魔導書

**単位**：1 項目＝1 ノート。
- 種別：`用語`（言葉の定義）／`設備`（物・システム）／`取り決め`（業務フロー、手順、社内ルール、方針、締め日・承認者などの決まり）。フォルダでは分けず、種別は frontmatter の `type` と索引で管理する。
- frontmatter：`type`、`aliases`、`status`（候補／確定）、`sources`（1 件以上必須。資料室や素材へのリンク、URL）、`basis`（原文／推論）、`confidence`（高／中／低）、`verified_on`、`used_by`（参照したクエスト id。`board.py` が数える）、`last_used`、`links`。
- 索引 `spellbook/魔導書.md`：1 項目 1 行（名前・aliases・種別・状態・使用クエスト数）。`board.py` が作り直す。
- 入れるもの：2 つ目のクエストでも使えそうな知識だけ。クエスト限りの事実は quest.md／冒険日誌に残す。依頼主個人の好みは人物伝。
- 上限 200 項目。超えたら、`last_used` が古い順に整理候補として質問に出す（1 年使われていない項目も同じ）。「第 2 の脳」になるのを防ぐ。

**参照の流れ（トークンを抑える順）**
1. 作業の前に、`board.py` が達成条件の語で `spellbook-find` を実行し、aliases が一致した項目（1 回 5 件まで）を依頼書に付ける。占い師・冒険者・錬金術師・鑑定士が読む。索引は読まない。
2. 足りなければ vault の Grep、最後に Web。リンクは 2 段まで。
3. 使った項目を達成条件の `refs` に記録する。クエスト票の記録に「参考にした魔導書」として出る。
4. 分からない語は報告書の `## 用語` に返す。
5. クエストが達成したら、魔法使いが未登録の項目を**候補**として書く（1 回 10 項目まで、出典つき）。候補は、使用クエストが 1 件以上あるものだけを依頼書に付け、「候補」と明記する。
6. 依頼主が質問タブで 1 項目ずつ「確定／修正する／あとで決める」を選ぶ。確定のときは、出典と根拠の種別を見せる。期限が来たら、候補のまま使う（5.7）。
7. **訂正**：要手直しの理由に `refs` の魔導書があれば、その項目を再確認候補として質問に出す。`verified_on` から 1 年たった項目も同じ。
8. `board.py shared-candidates` が、`sources` で結ばれた魔導書の項目の `used_by` が **2 件以上**の素材を資料室への移動候補として出す（規則で決まるので LLM を使わない。予測では移さない）。依頼主が承認すると、`board.py shared-move` が素材を移し、`input/` にリンクファイルを残し、`sources` を書き換える。

## 9. 資料室と設計図
- **資料室（`shared/`）**：実ファイルだけを置く。入れ方は、依頼主が画面から、または直接。`shared-candidates` の案を承認して移すのも入れ方。1 年使われていないファイルは整理候補（`housekeeping`）。
- **設計図（`templates/`）**：会社のひな形。鍛冶師が納品物を作るときに使う。占い師が、納品物の形が Office のときに設計図を選び、達成条件の `template` に書く。依頼主は画面から追加できる。使用回数と最後の使用日を `board.py` が数え、1 年使われていないものは整理候補にする。

## 11. 画面（`board.html`）
- 1 枚の HTML。CDN なし、オフラインで動く。画面は 10 秒ごとに `board.json` を読み直す。画面が書くのは `requests/` と `answers/` だけ。
- **タブ**（0.1 は 3 つ、0.2 で 5 つ）：**受付**（依頼を出す・ファイルを選んで素材に保存）／**クエスト**（一覧、詳細、道のり図、納品物へのリンク）／**質問**（未回答だけ、件数バッジ）／**予定表**（ガント＋締切。ゆとりが小さいものを強調。0.2）／**資料室・魔導書**（ファイルの追加、候補の確定。0.2）。
- 先頭に「いま何をするか」を 1 行と 1 ボタンで出す（質問・承認待ち・納品物の確認を先頭に）。
- **質問**：1 画面 1 問。図 1 枚＋選択肢 2〜4 個＋自由入力＋「あとで決める」。各選択肢に推奨と理由を 1 行。「選び直す」で未回答に戻せる。答えた直後に「あなたの選択：○○。取り消す」を出す。期限と、期限が来たときの進め方（推奨案）を見せる。**まとめて回答の画面はない**。
- **承認**：ボタンは「承認する／やり直す／あとで決める」の 3 つ。道のりの承認は道のり図、納品物の承認は達成条件ごとの結果の一覧（全部問題なければ 1 回で通せる）。納品物の承認の画面で good／bad と一言を付ける（空でも止めない）。実行の承認は、元に戻せない操作の内容を 1 画面で見せる。道のりの軽微な並べ替え（範囲内）は通知だけで、再承認は範囲の拡大か締切超過のおそれがあるときだけ。
- 達成条件の詳細に「念入りに作る」（より時間がかかり、費用が増える旨を説明つき）を置く。
- **図**：`board.py` が作るインライン SVG。色だけで区別せず、形・ラベル・`title`/`desc` を付ける。図の下に 1 行の文章要約。
- **ファイルの追加**：画面でファイルを選ぶと、そのクエストの `input/` または `shared/` に直接保存する。クエストができる前の依頼は `requests/files/` に置き、受付でフォルダができたら移す。
- **場所の見せ方**：
  - 素材・納品物・冒険日誌・設計図・資料室は、名前の横に「パスをコピー」ボタンを付ける。英語のフォルダ名は、画面には出さない。
  - ファイルを追加する直前だけ、保存先の確認として「保存先：素材（`guild/quests/Q1 見積り/input/`）」を出す。保存後は、保存したファイル名を出す。
  - ブラウザは選んだフォルダの絶対パスを取れない。`/guild:init` が vault の絶対パスを `board.json` の `vault_path` に書き、画面はそれと相対パスをつないで、コピーするパスを作る。
  - ファイルの選択欄の見出しには、保存先の名前（素材／資料室）を必ず書く。
  - 同じ名前のファイルがあるときは上書きせず、`-2` を付けて保存し、その旨を出す。
- 画面の値は必ずエスケープして描く。

- 1 文に 1 つの内容。40 字を目安にする。
- 主語と述語を書く。
- 指示語（これ・それ・あれ）を使わない。
- 能動態で書く。
- 手順は 1 文に 1 つの動作。
- 曖昧な語（適宜・など・いろいろ）を使わない。
- 日付は「3月8日」の形にそろえる。

### 13.1 工房（`/guild:workshop [Q番号|G番号]`）
**目的**：依頼主が会話しながら、素材を足し、納品物を作る。そこで分かったことを、次回以降に使える形で残す。

**使い方は 2 つ**：(a) NG の納品物を依頼主がテコ入れする。(b) 依頼主が自分で納品物を作るときの実行役。対象は、達成条件の状態が **待機** か **要手直し** のもの（確認待ちの納品物を直したいときは、先に「やり直す」を選ぶ）。新しい依頼は、先に受付嬢が受ける。

**1 回の流れ**
1. **開始**：達成条件が 冒険中 になる（待機→冒険中（工房）、または 要手直し→冒険中）。`board.py workshop-brief G1` が、短い前置き（達成条件、`done_when`、これまでの経過の抜粋、人物伝の要約、該当する掟の抜粋、一致した魔導書の項目［3 件まで］、同じクエストの前回の知見メモ［直近 1 件］）を作る。LLM は使わない。
2. **素材を足す**：依頼主がファイルの場所（またはテキスト）を渡す。`board.py input-add G1 <場所>` が、安全の検査（16 節）をしてから `input/` に写し、記録する。画面から足してもよい。
3. **対話で作る**：メインセッションが、1 問ずつ（図つき、選択肢つき）聞きながら下書きを作る。版は `output/.work/<名前>.v1.md`、`.v2.md` のように残す。**工房の間は、メインが錬金術師の役を兼ねる**（サブエージェントを呼ばない。往復のたびに文脈を読み直すコストを避けるため）。Word・Excel・PowerPoint・PDF にする最後の 1 回だけ、鍛冶師を呼ぶ。納品物の書式は 4.1 に従う。
4. **終了**：依頼主が「おしまい」を選ぶと、`board.py workshop-close G1` が、最新の版を正式な名前で `output/` に置き、`pre-check` を実行して状態を進める。鑑定は任意（依頼主が選ぶ）。承認②は必須。
   - 冒険中→鑑定中（鑑定を頼んだとき）／冒険中→確認待ち（工房）（鑑定を省くとき）。
5. **ふりかえり（知見メモ）**：メインが、会話の内容から `.system/reports/W<日時>-workshop.md` を書く（追加の呼び出しなし）。節は固定：`## 素材`（足したもの。ほかのクエストでも使えるか）／`## 用語・取り決め`（出典つき）／`## 好み・直しの傾向`（依頼主の発言の引用つき）／`## 直した点`（`fix_kind`・`point_code`・対象つき）／`## 設計図にできるか`。

**知見の行き先（次回以降に使われる仕組み）**
| 知見 | 行き先 | いつ・誰が | 次回以降の使われ方 |
|---|---|---|---|
| 業務用語・設備・取り決め | 魔導書（候補） | クエスト達成時に、魔法使いが知見メモの `## 用語・取り決め` を読んで書く。依頼主が確定 | `spellbook-find` で、依頼書に付く |
| 依頼主の好み・直しの傾向 | 人物伝（案） | クエスト達成時に、案があれば吟遊詩人が 1 回まとめて書く（`profile_pending` で数える）。依頼主が確定。推測は 2 回観察されるまで案のまま | 受付嬢・占い師・錬金術師・工房が、10 行の要約を読む |
| 同じ直しの繰り返し | 掟 | `## 直した点` を、鑑定の NG と同じ数え方（`fix_kind`＋`point_code`＋対象）で数え、2 回目で掟の案を出す（5.3） | 該当する役が、掟を読む |
| ほかでも使える素材 | 資料室 | 魔導書の項目の `used_by` が 2 件以上になったとき、`shared-candidates` が出す。依頼主が承認 | 素材の代わりに参照される |
| 出来のよい納品物 | 設計図（候補） | 依頼主に「これをひな形にしますか」と聞く（質問）。承認されたら `templates/` に置く | 占い師が設計図を選ぶとき、鍛冶師が使う |
| 作業の経過 | 冒険日誌、クエスト票の記録 | `workshop-close` が書く。クエスト票には「工房で作業した」と出る | 依頼主が進み方を見る |

- 知見メモは、処理した役（魔法使い・吟遊詩人）が `board.py memo-done` で処理済みにし、`済/` に移す。同じメモは二重に処理しない。
- 工房のために、サブエージェントを新たに呼ばない。
- 工房を途中で閉じたときも、`workshop-close --abort` が、そこまでの版と知見メモを残す。
- 工房中のメインのモデルは、依頼主の設定に従う（強制できない）。コストを抑えるときは sonnet を勧める。

## 14. 自動実行
- `guild-run.py`：OS のスケジューラ（Windows は `schtasks`、Mac/Linux は `crontab`）から、まず `board.py apply-simple` を実行し、次に `board.py need-claude` が yes のときだけ `claude -p "/guild:quest auto"` を呼ぶ。
- `need-claude` が yes になる条件：新しい依頼（R）や追加素材（U）がある、回答がそろって進められる質問がある、出発できる達成条件がある、鑑定・分解・聞き取りなど Claude が要る作業がある、蓄積（魔法使い・吟遊詩人）の作業がある。承認待ちや質問待ちだけなら yes にならない。
- 進捗のない回が 2 回続いたら、自動実行を止めて知らせる。
- **錠**（`run.lock`）で二重起動を防ぐ。成功したら消す。失敗した回は 1 時間残し、無駄な再試行を防ぐ。1 時間たった錠は、古いものとして捨てる。
- `allow.txt`：自動実行で許すツールの一覧。`--model` で使うモデルを選べる。
- 実行ごとに `usage.jsonl` を残す（失敗しても回は失敗にしない）。ログは 30 件まで。`usage.jsonl` は 90 日分を残し、古いものは月ごとの集計にまとめる。
- 承認待ちが長く続くと、`tick` の知らせ（5.7）が画面の先頭に出る。

## 15. 振り返りと自動改善
学習のループは、どれも「観測 → 蓄積 → 誰が次回どこで読むか → 訂正・削除」で閉じる。

| ループ | 観測 | 蓄積 | 次回の読み手 | 訂正・削除 |
|---|---|---|---|---|
| 掟 | 鑑定の NG、依頼主の「やり直す」、工房の直した点 | `.system/rules/`（再発数つき） | 該当する役（1 ファイル 20 行まで） | 半年再発なし・再発が減らない・矛盾は、`housekeeping` が質問にする |
| 教訓帳 | bad の理由、失敗した達成条件 | `.system/lessons.md`（100 行まで。掟になった行は畳む） | 占い師と鑑定士（該当する分類だけ。`lessons-brief`） | 100 行を超えたら古い順に畳む |
| 魔導書 | 達成したクエスト、工房の知見メモ | `spellbook/`（候補→確定） | 依頼書に付く（5 件まで） | 要手直しの理由に出た項目と、確認から 1 年の項目を再確認。上限 200 |
| 人物伝 | good／bad、インタビュー、工房の好み | `profile.md`（`evidence`・`kind` つき。50 項目まで） | 10 行の要約（受付嬢・占い師・錬金術師・工房） | 超えたら古い順に整理候補。矛盾・変化は依頼主が確定のときに直す |
| 設計図 | good の納品物 | `templates/`（使用回数つき） | 占い師・鍛冶師 | 1 年使われないものは整理候補 |
| 資料室 | 使用クエストが 2 件以上の素材 | `shared/` | 依頼書の素材として | 1 年使われないものは整理候補 |
| 見積・費用 | `usage.jsonl`、`estimate_min` と `actual_min`、effort と NG 率 | `calib.json` | 占い師の依頼書（補正係数 1 行） | 月ごとに再集計。opus に上げる条件の見直し案を出す |

- **good／bad**：納品物の承認の画面で付ける。bad のときは、理由（選択式＋一言）も付く。吟遊詩人が、クエスト達成時に教訓にする。good は、人物伝の「観察」と、設計図化の質問に使う。
- **インタビュー**：依頼主が頼んだときだけ。吟遊詩人が質問を作り、依頼主が質問タブで答え、吟遊詩人が人物伝の案に整理する。依頼主が確定する。
- **`housekeeping`**：1 日 1 回（`tick`）、整理候補を最大 5 件ずつ質問にする。

## 16. 安全
- 依頼主が選んだファイルは、保存先を `input/`・`shared/`・`requests/files/` に限り、パスの `..`・絶対パス・シンボリックリンクを拒否する。ファイル名の制御文字を除く。大きさに上限を置く（既定 50 MB）。
- 依頼主が入れたデータは、扱ってよいものとして扱う。認証情報が含まれていても、検出・拒否・質問はしない（責任は依頼主）。
- 承認の辺は、`answers/` に対応する回答の記録がない限り、`board.py` が通さない（5.5）。
- 依頼主の確認が要る操作（確定、実行）を、ギルドマスターが勝手に実行しない。

## 19. 受入条件
版を付ける。付けないものは 0.1.0。
- クエストを作ると、`input/`・`output/`・`adventure log/`・`quest.md` ができる。クエスト以外の登録経路がない。
- 閉路のある道のりは承認待ちに進めない。`done_when` のない達成条件があると承認待ちに進めない。
- `board.py set-status` が、`transitions.json` に無い辺、許されない役、満たされない述語を、終了コード 1 で拒否する。
- 承認の辺（`client`）は、`answers/` に対応する回答がなければ通らない。
- 納品物に書けるのは錬金術師と鍛冶師だけ（工房の間はメインも）。quest.md を書くのは `board.py render-quest` だけ。
- 承認①と承認②を通らないと、クエストは進行中にならず、達成条件は達成にならない。
- 同じ `fix_kind`＋`point_code`＋対象が 2 回出ると、掟の案の質問が出る。
- 質問は 1 問ずつ答えられ、「選び直す」で未回答に戻る。まとめ送信の画面がない。期限が来た質問は、推奨案で進む（承認は進まない）。
- 状態遷移に、到達できない状態・出口のない状態がない。失敗・中止した達成条件の後続は、依頼主への質問になる。サブエージェントの失敗は要手直しになる。
- 同時に 2 つの `board.py` が書いても、`board.json` が壊れない。壊れたときは `recover` で戻せる。
- `pre-check` が NG の達成条件は、鑑定士を呼ばずに要手直しになる。出典のない事実の行、前提のない推論の行を検出する。
- 1 回の実行で呼ぶサブエージェントが `limits.budget.max_calls`（既定 20）を超えない。超える場合はその回を止め、次の回が続きから進む。
- 既定のモデルが sonnet で、opus は 2.1-1 の条件のときだけ使われる（`usage.jsonl` で確認できる）。
- SKILL.md が 500 行以下（目標は 300 行）。テストがすべて通る。
- （0.2）道のり図と予定表が、`board.html` 単体（ネットなし）で表示される。魔導書の索引が `board.py` で作り直せ、`spellbook-find` が aliases で項目を返す。出典のない魔導書の候補は書けない。`housekeeping` が整理候補を質問にする。
- （0.3）依頼主向けの出力が、`lint-text` の検出できる規則（長さ・指示語・曖昧語・受け身の目印）に違反しない。
- （0.3）工房の終了時に知見メモができ、用語・取り決めは次の魔法使いの呼び出しで魔導書の候補になり、好みは人物伝の案になる（工房のために新しいサブエージェントを呼ばない）。`input-add` は、場所の検査（`..`・絶対パスの扱い・シンボリックリンク・大きさ）に通ったものだけを写す。
- （0.3）`need-claude` が no のとき、自動実行は Claude を呼ばない。

## 21. リスク
- 作り直しの規模が大きい。→0.1.0 は中核の 1 周だけにし、機能は段階で足す。
- サブエージェントの返答が 1 回であること、ファイル書込の仕様は、実装前に Claude の公式資料で確認する（未確認）。
- 承認が 2〜3 種あり、依頼主の負担になる。→承認②は一覧で 1 回、承認③は不可逆な達成条件だけ。ほかの質問は期限で進む。
- 魔導書・人物伝が肥大する。→上限と `last_used`、確定は依頼主、`housekeeping`。
- `transitions.json` の `guards` は述語の ID で、述語の中身は `board.py` が評価する。意味の検査（`done_when` を満たすか）は鑑定士が行う。
- 低コストのため sonnet を既定にすると、推論や分解の質が下がるおそれがある。→要手直し 2 回目と `effort: 高` で opus に上げ、`calib` の実績と鑑定の NG 率で見直す。
- 簡易日本語はチェッカーが不完全。→語彙表と簡易検査で最低限を担保する。
- LLM による推論の質は、鑑定士では保証できない。→推論に前提と確度を付けさせ、承認②で依頼主が判断する。
- 毎回読む文脈が増える。→人物伝・掟・教訓帳に行数の上限を置き、要約で渡す。
- 呼び出し回数の見積り（12〜17 回）は実測ではない。→0.1.0 で `usage.jsonl` を取り、見直す。
