# guild 再構築 SPEC

## 概要

- **目的**: 旧 guild の設計思想を変え、0ベースで作り直す。避けたいのは、達成内容がブレて、複雑化し、内容が薄くなること。
- **核（ひとつの仕事）**: 依頼主の課題を受け、Todo に分解し、自動実行できるものは自動で実行し、依頼主の実行が要るものは結果を待つ。成功・失敗・業務知識をノウハウとして溜め、次の依頼に活かす。
- **手法**: グラフエンジニアリング。進め方をデータ（グラフ）で持ち、実行側は辿るだけにする。
- **利用者**: 自分ひとり（個人利用）。
- **形態**: Claude Code プラグイン（skills / agents / commands）。旧版のコードは参照のみで、コピーせず新規に書く。日本語で書く。
- **世界観**: ギルド（RPG）の世界観・役名は残す。

## 流れ

1. **依頼**: 依頼主が課題を伝える。
2. **分解**: 依頼を Todo に分解し、Todo の依存グラフ（どれが先か）を作る。各 Todo に『自動実行／依頼主の実行』の種別と、合格基準（観点・合格ライン・確かめ方）を付ける。過去のノウハウを引いて参考にする。
3. **承認（1回だけ）**: 計画（Todo の一覧・種別・合格基準）をボードに出し、依頼主が承認または直す。以降は完了まで承認を取らない。ただし不可逆・外部公開の操作の前は、これまでどおり確認する。
4. **実行**: 前提が済んだ Todo から自動で進める。種別が『依頼主の実行』の Todo はボードで依頼し、結果（できた／できなかった、記録は任意で添付）の入力を待つ。
5. **合否**: 各 Todo を合格基準で判定する。満たさなければ実行に戻す。
6. **記録**: 成功・失敗・業務知識をノウハウとして溜める。
7. **納品**: 納品物（Markdown）を依頼主に渡す。

各 Todo の状態遷移（例：未着手 → 実行中 → 依頼主待ち → 合否待ち → 完了。不合格なら実行中に戻る）は、グラフ定義のデータとして持つ。

## データと置き場

- 作業中のプロジェクトのフォルダ内に `guild/` を作り、依頼ごとにサブフォルダを置く。状態・納品物・ノウハウをここに置く。
- 依頼主とのやりとり（計画の承認、依頼主の実行結果の入力）は、ボード（HTML）で行う。
- 依頼主が見るファイル（納品物など）は、Obsidian の Markdown 記法で書く（`[[リンク]]`、フロントマター、コールアウトなど）。

## 受入条件

1. 依頼を1件投げると、Todo の依存グラフと、各 Todo の種別・合格基準を含む計画がボードに出る。
2. 計画を承認すると、前提が済んだ Todo から自動で進む。承認を求めるのは計画の1回と、不可逆・外部公開の操作の前だけ。
3. 依頼主の実行が要る Todo は、ボードで依頼され、結果の入力まで待つ。入力後に続きが自動で進む。
4. 各 Todo は合格基準で判定され、満たさなければ実行に戻る。
5. 完了時に、成功・失敗・業務知識がノウハウとして `guild/` に溜まる。
6. 次の依頼の分解時に、関連するノウハウが引かれ、計画の参考にされる。
7. 納品物は Markdown で、Obsidian 記法で書かれている。
8. 進め方（Todo の依存関係と状態遷移）は、手順書の文章ではなくグラフ定義のデータで持っている。
9. 旧版のコードをコピーしていない。
10. 調べたことや主張を含む成果物は、事実と推論が分けて書かれ、事実には出典がある。この条件は、地図師が各 Todo の合格基準（`pass_line`）に書き、鑑定士が判定する。

## 非目標（最初の版では作らない）

- ノウハウの知識グラフ化（最初は単純な蓄積。溜まってから構造を決める）。
- Office 形式（Word・Excel・PowerPoint・PDF）の納品物。
- ノウハウによる SKILL.md など指示ファイルの自動書き換え（ノウハウは溜めて引くだけ）。
- 複数人・チームでの共有。
- Obsidian など外部ツールとの連携（記法の採用のみ）。

## リスク

| リスク | 対策・方針 |
|---|---|
| 機能を足すうちに複雑化し、同じ状態に戻る | 非目標を守る。役の追加は『機能追加で必要になったとき』に限り、追加の理由を決定ログに書く（役の数に上限は置かない：Q18）。 |
| 達成内容がブレて、内容が薄くなる | 核を『依頼 → Todo → 実行 → 結果 → ノウハウ』の一周に固定する。Todo ごとに合格基準を持たせ、満たすまでやり直す。 |
| 旧版の良い点を取りこぼす | コードは参照のみだが、考え方は git 履歴（`feat/guild-0.1`）から確認できる。引き継ぐ考え方は決定ログのとおり。 |
| ノウハウがプロジェクトごとに分かれ、依頼をまたいで溜まらない（Q17 の A） | 最初の版は受け入れる。問題が出たら共通の置き場を検討する。 |
| 計画の誤解釈のまま自動で進む | 計画の承認を最初の1回に置き、分解時に曖昧さを質問で解く。 |
