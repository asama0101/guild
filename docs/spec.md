# guild 再構築 SPEC

> 用語：この SPEC の「Todo」は、いまの文書と実装の「目標」（`goals`）。「地図師」は、いまの「受付係」。決定ログの旧名は、当時のまま残す。

## 概要

- **目的**: 旧 guild の設計思想を変え、0ベースで作り直す。避けたいのは、達成内容がブレて、複雑化し、内容が薄くなること。
- **核（ひとつの仕事）**: 依頼主の課題を受け、Todo に分解し、自動実行できるものは自動で実行し、依頼主の実行が要るものは結果を待つ。用語・業務フロー・業務情報・個人・心得を書庫（`archive/`）に溜め、次の依頼で全役が使う（`docs/archive-spec.md`）。
- **手法**: グラフエンジニアリング。進め方をデータ（グラフ）で持ち、実行側は辿るだけにする。
- **利用者**: 自分ひとり（個人利用）。
- **形態**: Claude Code プラグイン（skills / agents）。旧版のコードは参照のみで、コピーせず新規に書く。日本語で書く。
- **世界観**: ギルド（RPG）の世界観・役名は残す。

## 流れ

1. **依頼**: 依頼主が課題を伝える。
2. **分解**: 依頼を Todo に分解し、Todo の依存グラフ（どれが先か）を作る。各 Todo に『自動実行／依頼主の実行』の種別と、合格基準（観点・合格ライン・確かめ方）を付ける。書庫の関係する項目を引いて参考にする。
3. **承認（1回だけ）**: 計画（Todo の一覧・種別・合格基準）をボードに出し、依頼主が承認または直す。以降は完了まで承認を取らない。ただし不可逆・外部公開の操作の前は、これまでどおり確認する。
4. **実行**: 前提が済んだ Todo から自動で進める。種別が『依頼主の実行』の Todo はボードで依頼し、結果（できた／できなかった、記録は任意で添付）の入力を待つ。
5. **合否**: 各 Todo を合格基準で判定する。満たさなければ実行に戻す。
6. **記録**: 依頼の完了後、司書が用語・業務フロー・業務情報・個人・心得の候補を挙げ、依頼主が選んだものを書庫に溜める。
7. **納品**: 納品物（Markdown）を依頼主に渡す。

各 Todo の状態遷移（例：未着手 → 実行中 → 依頼主待ち → 合否待ち → 完了。不合格なら実行中に戻る）は、グラフ定義のデータとして持つ。

## データと置き場

- 作業中のプロジェクトのフォルダ内に `guild/` を作り、書庫（`archive/`）・納品物（`deliverables/`）・共通のインプット（`inputs/`）を置き、依頼ごとのフォルダや作業用のものは `.work/` に置く（Obsidian に出ない）。
- 依頼主とのやりとり（計画の承認、依頼主の実行結果の入力）は、ボード（HTML）で行う。
- 依頼主が見るファイル（納品物など）は、Obsidian の Markdown 記法で書く（`[[リンク]]`、フロントマター、コールアウトなど）。
- 個別の仕様の正本：データの形と `guild.py` のコマンドは `docs/graph-format.md`、ボードは `docs/board-design.md`、書庫は `docs/archive-spec.md`、役は `docs/roles-spec.md`。

## 受入条件

1. 依頼を1件投げると、Todo の依存グラフと、各 Todo の種別・合格基準を含む計画がボードに出る。
2. 計画を承認すると、前提が済んだ Todo から自動で進む。承認を求めるのは計画の1回と、不可逆・外部公開の操作の前だけ。
3. 依頼主の実行が要る Todo は、ボードで依頼され、結果の入力まで待つ。入力後に続きが自動で進む。
4. 各 Todo は合格基準で判定され、満たさなければ実行に戻る。
5. 完了時に、司書の候補から依頼主が選んだものが、書庫（`guild/archive/`）に溜まる。
6. 次の依頼で、全役が書庫の索引から関連する項目を引き、使った項目を報告に書く。
7. 納品物は Markdown で、Obsidian 記法で書かれている。
8. 進め方（Todo の依存関係と状態遷移）は、手順書の文章ではなくグラフ定義のデータで持っている。
9. 旧版のコードをコピーしていない。
10. 調べたことや主張を含む成果物は、事実と推論が分けて書かれ、事実には出典がある。この条件は、受付係が各 Todo の合格基準（`pass_line`）に書き、鑑定士が判定する。
11. 全 Todo が合格基準を満たしても、依頼主が納品物を確かめて「受け取る」を選ぶまで、依頼は完了にならない。「直してほしい」を選ぶと、コメントを添えて計画の作り直し（合格済みの Todo は引き継ぐ）になる。ギルドマスターが勝手に完了にしない。
12. 納品物は、各 Todo の成果物の寄せ集めではなく、それらをまとめた1つの資料（最後の「まとめの Todo」の成果物）である。出力は Markdown が既定（納品する目標は、依頼の `format` が `html` なら単一の `.html`）。PowerPoint・Excel などが要るときは、Claude Code に渡すプロンプトを `*.prompt.md` で出す。
13. 依頼主は、依頼を出すときに、共通のインプット（`guild/inputs/`）から既存のファイルを選べ、アップロードもできる。受付係は、依頼文と書庫のヒントから、関係するインプットを理由つきで選ぶ。依頼主は、承認の前後に追加・外すで直せる。納品物の型は、インプットに付けて依頼文で伝える。

## 非目標（最初の版では作らない）

- 書庫の知識グラフ化（種類別の項目と索引まで）。
- Office 形式（Word・Excel・PowerPoint・PDF）の納品物。
- 書庫による SKILL.md など指示ファイルの自動書き換え（書庫は溜めて引くだけ。心得の反映は人が行う）。
- 複数人・チームでの共有。
- Obsidian など外部ツールとの連携（記法の採用のみ）。

## リスク

| リスク | 対策・方針 |
|---|---|
| 機能を足すうちに複雑化し、同じ状態に戻る | 非目標を守る。役の追加は『機能追加で必要になったとき』に限り、追加の理由を決定ログに書く（役の数に上限は置かない：Q18）。 |
| 達成内容がブレて、内容が薄くなる | 核を『依頼 → Todo → 実行 → 結果 → 書庫』の一周に固定する。Todo ごとに合格基準を持たせ、満たすまでやり直す。 |
| 旧版の良い点を取りこぼす | コードは参照のみだが、考え方は git 履歴（`feat/guild-0.1`）から確認できる。引き継ぐ考え方は決定ログのとおり。 |
| 書庫がプロジェクトごとに分かれ、依頼をまたいで溜まらない（Q17 の A） | 最初の版は受け入れる。問題が出たら共通の置き場を検討する。 |
| 計画の誤解釈のまま自動で進む | 計画の承認を最初の1回に置き、分解時に曖昧さを質問で解く。 |
