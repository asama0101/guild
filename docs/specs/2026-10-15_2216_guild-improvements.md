# SPEC：guild 改善要望 4件

## 概要
- **目的**：guild（Claude Code プラグイン）を、(1) MCP を同梱せず環境の MCP を使い、(2) Todo の進捗と予定を見える化し、(3) 出力を Markdown に限り、(4) `guild/` を浅く・少なく整理して Obsidian で読みやすくする。
- **ゴール**：この SPEC の承認。承認後に、別途「改善プラン（実施項目・変更ファイル・順序・リスク）」を作る。実装はその後。
- **方針**：ロジックをシンプルに保つ（追加の判断・検査・連動を最小にする）。互換性は不要（既存の `guild/` の移行はしない）。外部ライブラリなし。「計画の承認は1回だけ」を維持する。進め方はデータ（`plan.json`）で持つ。

## 要望1：MCP を同梱しない
- `.mcp.json`（Playwright MCP の同梱）を削除する。
- 斥候（`agents/scout.md`）の `tools` は、環境の Playwright MCP のツール（`mcp__playwright__browser_*`）を列挙する。サーバー名 `playwright` を前提にし、README に明記する。
- 確認は `/guild:init` のときだけ行う。未導入・未接続なら、警告（導入方法つき）を出して `init` を止める（`guild/` を作らない）。代替手段へのフォールバックはしない。
- 導入後に MCP が外れて斥候が動けないときは、新しい検出は設けない。斥候の失敗として扱う（鑑定で不合格 → やり直し → 使い切ると `failed` で依頼主が判断）。
- README の「必要なもの」から Node.js（`.mcp.json` 用）を外し、Playwright MCP を足す。

## 要望2：Todo の進捗と予定の可視化
- **日付の項目**
  - 依頼：開始日（`start`。未指定は登録日）、締切（`due`。未定は登録日）
  - Todo：実行予定日（`scheduled`）、締切（`due`。既存の項目）。開始日はなし
- **決め方**：地図師が計画作成時に、依存関係から Todo の予定日・締切を決める。承認画面で確認できる。依頼の締切が未定（登録日）なら、Todo の予定日・締切もすべて同じ日になる。
- **変更**：依頼主は、ボードの Todo 一覧で Todo の予定日・締切を、依頼の開始日・締切とともに変更できる（入力の種類は既存の `due` を拡張）。変更は他の日付へ連動しない。
- **検査**：日付が `YYYY-MM-DD` の実在日かどうかだけをエラーにする。順序の矛盾（依存先より前の予定日、予定日が締切を過ぎる、など）はボードで警告表示にとどめる。遷移には使わない。
- **新タブ「クエスト進捗」**（ボードは8タブになる）
  - 上段：ガントチャート（HTML/SVG、外部ライブラリなし）。依頼は開始日〜締切のバー、全 Todo（`auto` と `human`）は予定日のマイルストーン。進捗は色と塗り（依頼バーは完了した Todo の割合）で表す。
  - 下段：`human` の Todo だけの、予定日ごとの件数。
  - 既定は進行中の依頼のみ。完了・中止の依頼は切り替えで含める。
- `docs/graph-format.md` と `plan.json` の形式を更新する。

## 要望3：アウトプットは Markdown に限定
- 最終納品物も中間成果物も Markdown のみ。`format` 項目と `FORMATS` を削除する。テンプレートは `.md` だけ受け付ける（ほかは理由を出して拒否）。
- PowerPoint・Excel などが必要なときは、Claude Code に渡すプロンプトを Markdown で出す。ファイル名は `*.prompt.md`（名前で判別。`plan.json` に項目は足さない）。
- 「Markdown 以外が必要」の判断は3つ。
  1. 依頼主の指定（依頼文）
  2. 地図師が計画作成時に、プロンプトを書く Todo を計画に入れる
  3. 冒険者が実行中に気づいたとき：自分の Todo の成果物として `*.prompt.md` を追加してよい。Todo は増やさず、承認は取らない。報告に追加した理由を書く（計画を変えず、不可逆・外部公開でもないので「承認は1回だけ」と衝突しない）。
- プロンプトは `deliverables/` に置き、ボードの「受け取りの確認」の手紙にも表示する（コピーしやすい形）。

## 要望4：`guild/` の構成
```
guild/
  board.html  config.json
  archive/        書庫（フラット：archive/用語名.md。種類は frontmatter の type で持つ。index.md あり）
  deliverables/   納品物と *.prompt.md（フラット：Q001_<元のファイル名>）
  inputs/         共通インプット（1つだけ。非 Markdown も置ける）
  templates/      テンプレート（.md）
  .work/          機械用・作業用（Obsidian に出ない）：Q001/（plan.json・request.json・reports/・output/・inbox/・prev/…）、requests/、web/、archive の inbox、inputs のバックアップ
```
- **納品物の置き方**：全 Todo が済んで「受け取りの確認」の手紙が出る時に、納品物の Todo（`deliverable: true`）の成果物と、どの Todo の成果物でも `*.prompt.md` を、`.work/Q###/output/` から `deliverables/` へコピーする（名前は `Q###_` ＋元のファイル名）。依頼主は Obsidian でも読んでから受け取れる。「直してほしい」（`replan`）になったら置いたものを消し、また全 Todo が済んだ時に置き直す。途中の成果物（材料）と役の報告は `.work/` に残し、Obsidian では見えない（ボードでは読める）。
- **インプット**
  - 共通の置き場 `guild/inputs/` に1つだけ置く。各依頼は `request.json` にファイル名で参照する。
  - 同じファイルの判定はファイル名だけ（大文字小文字は区別しない）、サブフォルダなし。内容が同じなら何もしない。内容が違えば上書きする。
  - 上書き前の古い版は `.work/` のバックアップ（上書きのきっかけの依頼ごと）に保存し、その依頼が閉じる（完了または中止）時に削除する。
  - 他の進行中の依頼も、上書き後は新しい版を読む（古い版は誤上書きの復元用だけ）。したがって「別の依頼が使用中の古い版を先に消す」問題は構造上起きない。他の依頼への通知はしない。
- **書庫のフラット化**：`ARCHIVE_DIRS` と `retype` の移動処理を、frontmatter の `type` の書き換えに置き換える。種類をまたぐ同名は、既存の「同名・別名は更新の候補」規則で防ぐ。

## 受入条件
1. `.mcp.json` がなく、`/guild:init` は Playwright MCP が未導入・未接続だと警告して止まり、`guild/` を作らない。接続済みなら、従来どおり `guild/` ができる。
2. 計画に、依頼の開始日・締切と、各 Todo の予定日・締切が入る。承認画面で確認でき、ボードで変更できる。日付の形式が不正なら拒否される。順序の矛盾は警告表示になる。
3. 新タブ「クエスト進捗」に、ガント（依頼のバー・全 Todo のマイルストーン・進捗の色と塗り）と `human` の日別件数が出る。外部ライブラリを使わない。既定は進行中の依頼のみ、切り替えで完了・中止も含む。
4. `format` 項目がなく、テンプレートは `.md` だけ受け付ける。`*.prompt.md` が `deliverables/` に置かれ、「受け取りの確認」の手紙にコピーしやすい形で出る。冒険者が実行中に追加しても、承認は求められない。
5. `guild/` が上の構成になる。納品物が全 Todo 済みの時に `deliverables/Q###_…` に置かれ、`replan` で消えて置き直される。
6. 同名のインプットを置くと上書きされ、古い版が `.work/` に残り、上書きした依頼が閉じると消える。内容が同じなら何も起きない。
7. 書庫が `archive/用語名.md`（フラット）で、登録・編集・種類の変更・索引・心得を読まない決まりが今まで通り動く。
8. `tests/test_guild.py` が通る。README・`docs/`（`spec.md`・`graph-format.md`・`board-design.md`・`archive-spec.md`・`roles-spec.md`）・各 `agents/*.md`・`SKILL.md`・フック（`web_gate`）が新しい構成に合う。

## 非目標
- 既存の `guild/` のデータ移行（互換性は不要）。
- MCP の同梱、代替手段へのフォールバック、実行中の MCP 検出。
- 日付の矛盾のエラー化、日付の自動ずらし（連動）。
- 古い版を他の依頼が読み続ける仕組み、上書きの通知。
- 途中の成果物（材料）と役の報告を Obsidian で見えるようにすること。
- Markdown 以外のファイルそのものを guild が作ること（プロンプトを出すだけ）。
- 外部ライブラリの利用、ローカルサーバー。

## リスク
- **`.work/`（dot フォルダ）をボードが読めるか**：File System Access API で開けるかは未確認。実装の最初に確かめ、だめなら名前を変える（例：`_work/`）が、Obsidian に出る可能性がある。
- **書庫のフラット化**：種類をまたぐ同名の項目、`retype` と索引・ボードの書庫タブの書き換え範囲が広い。心得（`lessons`）を役が読まない決まりを、フォルダではなく `type` で守る必要がある。
- **構成の変更が広い**：`guild.py`・`board.html`・`web_gate`・各指示書・テスト・docs のパスがすべて動く。互換性は不要なので、一括で置き換える。
- **MCP の接続判定**：`init` が「接続済み」を判定する方法（ツール一覧か `claude mcp list` か）は未確認。
- **導入後の MCP 切れ**：検出せず失敗の経路に乗せるので、依頼主には原因が分かりにくい。報告に原因を書く指示を斥候に入れる。
- **冒険者の `*.prompt.md` の追加**：承認なしで増えるので、報告に理由を書く決まりを鑑定の確認項目に入れる。
- **インプットの上書き**：進行中の他の依頼が、前提の変わったファイルを黙って読む。バックアップは誤上書きの復元用だけ。
